# US-2.2 — `ripe sync`: Skill Resolution, Event Submission & Outcome Reporting

**Slice**: 3 — Core Pipeline  
**Status**: Ready for planning

## User Story

As the telemetry system, skill invocation events from the just-closed session transcript are
submitted to the server, deduplicated by `(session_id, tool_use_id)`. As a developer, running
`ripe init` tells me my git identity (email, display name) will be collected and attached to
those events, before it happens. If a `sync` run fails, I find out — clearly, and only when I'm
next looking, since the hook that triggers it can't talk to me directly.

## Context

This story introduces `ripe sync` itself: the `SessionEnd` hook that triggers it, its
detached-execution model, and everything it does in two sequential phases.

**Phase 1 — skill resolution.** Reuses the `POST /api/skills` endpoint and `.ripe/cache.json`
format defined in [US-2.1](2026-06-21-us-2.1-skill-registration.md), but with its own,
`sync`-specific resolution strategy: lazy, triggered by invocation rather than a full scan. For
each `Skill` invocation found while parsing the transcript (the same parse Phase 2 does) whose
name is absent from `.ripe/cache.json`:

1. Checks it's committed on main branch; if not, skips it — recorded in the local outcome file:
   "skill X not on main, skipping"
2. Skips namespaced skills (containing `:`) — recorded in the local outcome file
3. Otherwise POSTs it to `POST /api/skills` and writes the returned `skill_id` to
   `.ripe/cache.json`

If `.ripe/settings.json` doesn't exist (i.e. `ripe init` was never run in this project), `sync`
exits 0 silently — there's nothing to sync.

**Phase 2 — event submission**, running after Phase 1 has resolved all IDs it can. Parses the
`.jsonl` session transcript, extracts `Skill` tool invocations, and POSTs them in a single batch
(ADR-001).

Deduplication ensures that re-submitting the same transcript (e.g. after a crash) never inflates
counts. Developer identity as `git config user.email` was decided in
[ADR-002](../../architecture/decisions/ADR-002-developer-identity-source.md); this story adds a
display name alongside it (`git config user.name`) and the one-time-per-run consent notice.
Identity is read live at submission time, not cached — local git config can change between syncs.

No identity is stored server-side beyond what's submitted per-event — no users table, no
persistent consent flag.

**Detached execution:** `ripe sync`, when invoked by the `SessionEnd` hook, runs detached from the
parent process per [ADR-001](../../architecture/decisions/ADR-001-sessionend-hook-transcript-parsing.md)
— the hook returns immediately (validated empirically: no felt delay on `/exit`/`/clear`/window
close), so neither phase has a terminal to write to. Non-fatal issues from *either* phase are
recorded in the local outcome file instead. Stays silent on success; on failure, the *next* `ripe`
invocation surfaces a warning — there's no synchronous point left to report success or failure at
exit time, since the parent (and often the terminal) is already gone by the time the detached work
completes.

**The outcome file** (`.ripe/last-sync.json`, gitignored) is what makes any of the above visible
at all. Schema:

```text
{
  status: 'success' | 'failure'
  failedPhase?: 'skill-resolution' | 'event-submission'   // present only if status is 'failure'
  message: string                                          // human-readable, shown verbatim
  sessionId?: string                                       // the session this run processed
  transcriptPath?: string                                  // reserved for a future manual-retry
                                                             // feature; not acted on in v1
  timestamp: string                                         // ISO 8601, when this run finished
}
```

Written once per `sync` run, overwriting the previous entry. Read by the *next* `ripe` invocation
(`init` or `sync`): if `status` is `'failure'`, that invocation prints `message` to stderr before
doing its own work; a `'success'` entry (or a missing file) prints nothing. This is also the
mechanism behind [US-1.3](2026-07-25-us-1.3-remote-derived-project-identity.md)'s stale-cache
recovery message ("delete `.ripe/cache.json` and run `ripe sync` again") and behind the
"skill/event skipped" notices from both phases above — they're all just different `message`
values written to this same file.

## Scope

**In scope:**

- `ripe init` adds the `SessionEnd` hook to `.claude/settings.local.json` if not present
- `ripe sync` command: detached spawn on invocation, per ADR-001
- Phase 1 of `ripe sync`: lazy, invocation-triggered skill resolution (reusing US-2.1's endpoint
  and cache format)
- `POST /api/events` server endpoint
- Phase 2 of `ripe sync`: parse transcript, resolve IDs, submit batch
- Recheck transcript `.jsonl` structure against latest installed Claude Code CLI version on minor/major
  bump, or quarterly minimum ([version-1-scope.md](../versions/version-1-scope.md#ongoing-transcript-format-recheck));
  update parser + [stability doc](../../architecture/analysis/transcript-format-stability.md) if changed
- Server-side deduplication on `(session_id, tool_use_id)`
- `ripe init` prints a consent notice to stderr, every run, informing that `git config user.email`
  and `git config user.name` will be collected and submitted with skill invocation events —
  notice-only, no stored flag, no per-developer confirmation gate
- `ripe sync` reads `git config user.email`/`user.name` live at submission time; either missing →
  no event submitted at all (recorded in the outcome file, no request made, exit 0)
- The outcome file (`.ripe/last-sync.json`): schema above, write conditions for both phases, and
  the read/surface behavior on the next `ripe` invocation

**Out of scope:**

- Non-Skill tool invocations (ignored)
- Retry logic on network failure (log and exit 0)
- Automatically acting on `transcriptPath` for a retry (field is recorded, not yet consumed)
- Persistent consent flag or first-run confirmation gate (dropped — see project design-questions
  memory, resolved 2026-07-25)
- Server-side users table / identity persistence beyond per-event fields
- Org-level admin opt-out of identity collection

## API Contract

```text
POST /api/events
Body: Array<{
  eventType: string     // "skill_invocation" (only kind in v1; envelope allows future kinds)
  timestamp: string     // ISO 8601
  userEmail: string     // git config user.email, read live, always non-empty
  userName: string      // git config user.name, read live, always non-empty
  projectId: string     // from local cache
  sessionId: string     // Claude Code session ID
  clientType: string    // source adapter, e.g. "claude-code"
  payload: {
    skillId: string      // from local cache (server-assigned)
    skillName: string    // current name at time of submission
    toolUseId: string    // unique per invocation within the session
  }
}>
→ 204 No Content
→ 400                    (unknown projectId or skillId — see server-side validation below)
```

Server behavior: bulk insert with `ON CONFLICT(session_id, tool_use_id) DO NOTHING` (`tool_use_id`
read from `payload` for this event type; DB columns stay snake_case, only the JSON wire fields
above are camelCase). The server also validates that `projectId` and every `payload.skillId` exist
before inserting — an unknown ID rejects the whole batch with 400 rather than silently accepting
orphaned rows. This is what a stale/cleared local cache relies on to be detectable at all (see
[US-1.3](2026-07-25-us-1.3-remote-derived-project-identity.md)'s stale-cache recovery).

Envelope (`eventType`, `timestamp`, `userEmail`, `userName`, `projectId`, `sessionId`,
`clientType`) is common to any future event kind; `payload` shape is specific to `eventType`.
No other event type is scoped yet — this shape is adopted now, before the contract ships, to avoid
a breaking change later.

## CLI Behavior

**`ripe init`:**

1. Prints consent notice to stderr (every run): identity (email, display name) will be collected
   and submitted with telemetry events
2. Adds the `SessionEnd` hook to `.claude/settings.local.json` if not already present
3. If the outcome file records a `'failure'` from the last `sync` run: prints its `message` to
   stderr before continuing

**`ripe sync`** (invoked by the `SessionEnd` hook; spawns a detached child per ADR-001 and returns
immediately — everything below runs inside that detached process):

0. If `.ripe/settings.json` does not exist: exit 0 silently (project not initialized via `ripe init`)
1. If the outcome file records a `'failure'` from the last run, that will be printed on the next
   *interactive* `ripe` invocation, not here (no console to print to)
2. **Phase 1** (skill resolution): see Context above
3. **Phase 2** (event submission):
   1. Parses the `.jsonl` transcript for `Skill` tool use entries
   2. Skips non-Skill tool uses
   3. Skips namespaced skills (containing `:`), recorded in the outcome file
   4. Resolves `skill_id` from the local cache (populated in Phase 1); if a skill invoked isn't in
      the cache after Phase 1 (not on main, or namespaced), skips that event, recorded in the
      outcome file
   5. Reads `git config user.email` and `git config user.name`; either unset → recorded in the
      outcome file, no request made, exit 0
   6. Sets `clientType` to `"claude-code"` on every event
   7. Sends all events in one POST
   8. If no skill invocations found: exits 0, no request made, nothing recorded (not a failure)
   9. If server unreachable: recorded in the outcome file, exits 0; next `ripe` invocation
      surfaces the failure
4. Writes the outcome file (schema above) reflecting the result of Phase 1 and/or Phase 2

## Acceptance Criteria

- [ ] `ripe init` adds the `SessionEnd` hook to `.claude/settings.local.json` if not already present
- [ ] `ripe sync` runs in a detached child process; the parent returns near-instantly regardless
      of network conditions
- [ ] `ripe sync` exits 0 silently if `.ripe/settings.json` doesn't exist (project never `init`'d)
- [ ] `ripe sync` resolves only invoked skills absent from `.ripe/cache.json` (lazy, on demand),
      after checking each is committed on main
- [ ] Skills not on main, or namespaced, are skipped during resolution, recorded in the outcome file
- [ ] All skill invocations in the transcript are submitted in one request
- [ ] An invocation whose skill couldn't be resolved (not on main / namespaced) is skipped from
      the event batch, recorded in the outcome file
- [ ] Duplicate submissions (same `sessionId` + `toolUseId`) are ignored by the server
- [ ] No request made if the transcript contains no skill invocations
- [ ] Non-Skill tool uses are ignored
- [ ] Server unreachable (either phase) → recorded in the outcome file, exit 0 (does not block
      session close)
- [ ] Every submitted event carries `clientType: "claude-code"`
- [ ] `ripe init` prints a consent notice to stderr on every run (blocking command, direct feedback)
- [ ] No consent flag is written to `.ripe/cache.json`, `.ripe/settings.json`, or anywhere else
- [ ] `ripe sync` reads `user.email`/`user.name` fresh from git config on every run, not cached
- [ ] Missing `user.email` or `user.name` → recorded in the outcome file, no event submitted, exit 0
- [ ] `POST /api/events` with an unknown `projectId` or `skillId` returns 400
- [ ] The outcome file matches the schema above and is overwritten (not appended) each `sync` run
- [ ] A `'failure'` outcome is silent at `sync`'s own exit time, then printed by the next `ripe`
      invocation; a `'success'` outcome (or missing file) prints nothing
- [ ] Transcript format recheck cadence (CLI minor/major bump, or quarterly) is documented and
      tracked as an ongoing v1 commitment, not a one-time check
