# US-1.3 — Remote-Derived Project Identity

**Slice**: 1 — Foundation & Project Registration
**Status**: API slice done, including `remote_url` persistence and HTTPS-only enforcement — manual
git-reachability verification (see "Definition of Done" below) confirmed all four fixtures
reachable via `git ls-remote` on 2026-08-02. CLI slice partially done — `ripe init` reads the real
`origin` remote via `git remote get-url origin` and forwards it (no more hardcoded placeholder),
and now prompts for an HTTPS equivalent when that remote isn't HTTPS, with the CLI's own error
message distinguishing an unreachable server from one that rejected the remote (see "CLI Behavior"
below) — but the `.ripe/settings.json`/`.ripe/cache.json` split and the rest of this story's CLI
acceptance criteria (no short-circuit on re-`init`, idempotent 200/201 handling without a
confirmation prompt, `.ripe/config.json` retirement) aren't implemented yet. All of this ships via
further commits on [PR #49](https://github.com/paulelian-tabarant/ripe/pull/49) /
`feat/api/1-3-use-repo-remote-origin-as-project-registration-key`, not a separate branch/PR.

## User Story

As a developer, running `ripe init` on a project I've already registered (or that a teammate
already registered) just works — no manual confirmation, no committed config file, no risk of
silently attaching to the wrong project.

## Context

[US-1.1](2026-06-21-us-1.1-project-registration.md) keyed project uniqueness on the directory
name and required a committed `.ripe/config.json` so team members could share the same
`project_id`. This user story supersedes that behavior per [ADR-018](../../architecture/decisions/ADR-018-remote-derived-project-identity.md)
— US-1.1 itself is shipped and stays as a historical record; this story describes the new
behavior that replaces it.

Project identity moves to a canonicalized `origin` git remote URL (`repo_key`). Local state splits
into two gitignored files: `.ripe/settings.json`, holding only the interactively-configured
`serverUrl` (unchanged from US-1.1); and `.ripe/cache.json`, holding everything server-resolved or
derived — `project_id`, the skill ID cache introduced by [US-2.1](2026-06-21-us-2.1-skill-registration.md)
(itself not yet shipped), and `last_synced_sha` (for a future slice). `.ripe/config.json` is
retired — nothing in either new file is committed.

## Scope

**In scope:**

- `repo_key` column (`UNIQUE`) on the `projects` table; `name` becomes a non-unique display field
- `POST /api/projects` becomes find-or-create on `repo_key` (idempotent, no 409/confirmation flow)
- **Normalization is server-side**: the API receives the raw `origin` remote URL and computes
  `repo_key` itself — the server is the single source of truth for what counts as "the same
  repo," so convergence doesn't depend on every client (current or future) normalizing
  identically
- CLI reads `git remote get-url origin` and forwards the raw string as-is — no normalization
  logic on the client
- No `origin` remote → hard error, no fallback to directory name
- `project_id` may be cached locally (gitignored) as a call-skipping optimization, never committed
  — a missing/stale cache entry just triggers a re-resolve via `repo_key`, no ambiguity
- Local state splits into `.ripe/settings.json` (gitignored: `serverUrl` only, interactively set
  by `ripe init`) and `.ripe/cache.json` (gitignored: `project_id` cache, skill ID cache, and any
  other server-resolved/derived state introduced by later slices, e.g. `last_synced_sha`)
- `.ripe/config.json` retired
- `remote_url` column (`NOT NULL`, no uniqueness constraint) on the `projects` table, holding a
  **normalized HTTPS form** of the remote — `https://{resource}/{owner}/{name}`, computed
  server-side from the raw `remoteUrl` once at creation and never updated afterward (a
  `POST /api/projects` call for an already-existing `repo_key` doesn't touch its stored
  `remote_url`, even if a different equivalent form of the remote was sent). Critically, this uses
  `git-url-parse`'s `resource` field, not `source` — `source` is the field `repo_key` is built
  from, and it applies a lossy heuristic that can silently mangle the literal host (e.g. a real
  observed case: `gitlab-forge.din.developpement-durable.gouv.fr` → `source` reports
  `din.developpement-durable.gouv.fr`, dropping `gitlab-forge.`); `resource` preserves the literal,
  unmangled hostname, which is what a connectable address needs. Any port present in the original
  remote (e.g. a custom SSH port) is dropped — it's almost always the SSH port, not necessarily
  valid for HTTPS access to the same host. `repo_key` remains the sole identity lookup;
  `remote_url` is never used for project resolution and isn't exposed on the wire. Brought forward
  from ADR-018's originally-deferred "Related, Deferred Decision: `remote_url` for Connectivity"
  addendum — computing and persisting the normalized address now, rather than waiting for the
  future capability (server-side repo-fetching for skill rename/delete reconciliation) that will
  consume it, avoids an unbackfillable gap for projects registered before that capability exists,
  since `repo_key` alone can't be reconstructed back into a connectable host later.
- **`remoteUrl` must be an `https://` remote — any other protocol is rejected with `400`**,
  reusing the existing `InvalidRemoteUrlError`/"unparseable remote" contract rather than a new
  status or error shape. This rejection applies to the *whole* registration, not just
  `remote_url` — a non-`https://` remote never reaches `repo_key` derivation either, even though
  `repo_key`'s own derivation logic has no such protocol restriction in principle. See
  [ADR-019](../../architecture/decisions/ADR-019-repository-state-synchronization.md) for the full
  rationale (a correctness problem deriving HTTPS hosts from SSH remotes, and forward compatibility
  with future SSO-based git host integrations).

**Out of scope:**

- Forks (naturally register as separate projects — no special handling)
- Repository rename/move detection (same accepted limitation as V1 skill rename)
- Multiple remotes beyond `origin`
- Automatic recovery when the server rejects a cached `project_id`/`skill_id` as unknown (e.g.
  after manual server-side data loss) — see "Recovery from a stale cache" below; automating it is
  deferred to a later slice
- Actually *using* `remote_url` for server-side repo-fetching (webhook handling, calling a git
  host's compare/fetch API) — this slice only computes and stores the normalized address; the
  fetching capability itself is v2 scope. See [ADR-018's connectivity
  addendum](../../architecture/decisions/ADR-018-remote-derived-project-identity.md#related-deferred-decision-remote_url-for-connectivity)
  for what that future capability still needs on top of this

## `repo_key` Normalization

Computed server-side, from the raw `origin` remote URL string the client sends, using the
`git-url-parse` library (handles scp-like SSH, `ssh://`, `https://`, `git://` forms uniformly;
see the implementation plan for why). `repo_key` is `${source}/${owner}/${name}` from the
library's parsed output — nested groups (e.g. GitLab subgroups) fall out naturally since `owner`
preserves the full path minus the last segment, and the port is a separate field the library
never includes in `source`.

**No case transformation is applied on top of the library's output** — `repo_key` is a
pass-through of whatever casing the library reports, not something we independently normalize.
This is deliberate, not an oversight: DNS hostnames are case-insensitive by spec, and the library
already lowercases `source` for `https://`/`ssh://` forms (via Node's WHATWG `URL`, which
lowercases hostnames per spec) — but *not* for scp-like SSH, where host parsing goes through a
custom regex with no case normalization. Org/repo path segments (`owner`/`name`) are never
lowercased by the library, in any form — those are server-side identifiers that may be backed by
a case-sensitive filesystem on self-hosted git servers, so assuming case-insensitivity there would
risk silently merging two genuinely distinct, differently-cased repos into one project. We trust
the library's judgment here rather than inventing a stronger normalization ourselves.

**Accepted limitation**: because the library only lowercases the host for `https://`/`ssh://`
forms (not scp-like), two developers whose `origin` remotes differ *only* in host casing across
those two shapes (e.g. `git@GitHub.com:org/repo.git` vs `https://github.com/org/repo.git`) would
resolve to different `repo_key`s and silently register a second project. In practice this
requires someone to have hand-typed or otherwise introduced a differently-cased host — every
major git host's UI always emits lowercase clone URLs — so this is accepted as the same shape of
rare, silent edge case as the ADR's other accepted risks (forks, repo rename/move, two unrelated
self-hosted servers colliding on the same path), not engineered around.

A `remoteUrl` that fails to parse into a valid host+path (via the library or our own validation of
its output) is treated the same as no `origin` remote at all: hard error, no fallback.

## `remote_url` Normalization

Also computed server-side, from the same parsed `git-url-parse` output as `repo_key`, but using
different fields for a different purpose: `remote_url` is `https://{resource}/{owner}/{name}`,
using the library's `resource` field for the host — never `source`. `resource` is the literal,
unmangled hostname; `source` (what `repo_key` uses) applies a provider-name heuristic that can
strip subdomains it guesses are vcs-hosting prefixes, which is fine for a lossy identity key but
wrong for an address meant to be reachable.

Any port present in the original remote is dropped, not carried into `remote_url` — a port on the
remote has no guaranteed relationship to that host's HTTPS port. No `.git` suffix is appended.

**Only `https://` remotes are accepted at all** (see "Out of scope" above) — a non-`https://`
`remoteUrl` is rejected with `400` before `repo_key`/`remote_url` derivation is attempted, the
same as any other unparseable remote. Because of this, `remote_url` derivation can never fail
independently of `repo_key` derivation failing — both are computed from the same successful parse
of an already-confirmed-`https://` remote.

`remote_url` is computed once, at creation, and never updated afterward — a repeat
`POST /api/projects` call for an already-registered `repo_key` returns the existing project
without touching its stored `remote_url`, even if the `remoteUrl` sent this time differs (e.g. a
teammate's git config emits a differently-formatted but equivalent HTTPS URL).

## API Contracts

```text
POST /api/projects
Body: { name: string, remoteUrl: string }
→ 201 { "projectId": "proj_<nanoid>" }                          (new project)
→ 200 { "projectId": "proj_<nanoid>" }                          (existing repo_key, idempotent)
→ 400                                                            (invalid body — e.g. missing
                                                                   remoteUrl, a remoteUrl that
                                                                   fails to normalize, or a
                                                                   remoteUrl that isn't https://)
```

The server normalizes `remoteUrl` to `repo_key` (see "`repo_key` Normalization" above) before the
find-or-create check. `repo_key` is `UNIQUE` on the server (DB column; not exposed on the wire);
`name` is stored but not constrained. No 409 case remains — the same `remoteUrl` (in any accepted
form) always resolves to the same `projectId` without confirmation. A normalized HTTPS form of
`remoteUrl` — `https://{resource}/{owner}/{name}` (see "`remote_url` Normalization" above) — is
also persisted to a `remote_url` column (`NOT NULL`, no uniqueness constraint, not exposed on the
wire), computed once at creation time only.

## CLI Behavior

**`ripe init`:**

1. Reads `origin` remote via `git remote get-url origin`; no remote → stderr error, exit 1
2. **If that remote isn't an `https://` URL** (e.g. the common scp-like SSH form
   `git@github.com:org/repo.git`), prompts the user to type the HTTPS equivalent instead of
   failing outright: `` Your git remote ("<remote>") isn't HTTPS. Enter the HTTPS URL for this repo: ``.
   Whatever the user types is used as `remoteUrl` from this point on, with no
   client-side re-validation — an invalid or still-non-HTTPS answer surfaces the same way any
   other rejected `remoteUrl` does, via the server's `400` (see step 4). This is a one-shot
   prompt, not a retry loop.
3. Reads project display name from the current working directory (unchanged from US-1.1)
4. POSTs `{ name, remoteUrl }` (the raw — or user-typed-HTTPS — remote string, unmodified) to
   `<server-url>/api/projects`
5. Server unreachable, or server responds `400` (unparseable `remoteUrl`, or a `remoteUrl` that
   still isn't `https://` after the prompt) → stderr error, exit 1. The error message must
   distinguish these two cases (unreachable server vs. rejected remote) rather than reporting a
   `400` as "could not reach server," which would be misleading.
6. Writes `serverUrl` to `.ripe/settings.json` (unchanged from US-1.1 — still interactively
   prompted; the only field in local state that isn't server-resolved or git-derived), and the
   returned `projectId` to `.ripe/cache.json`

**Accepted limitation**: the HTTPS-prompt answer (step 2) is never verified against the actual
repo — no ownership check, no reachability check at registration time (that's the deferred
`remote_url`-for-connectivity capability, see "Out of scope" above). A mistyped or wrong-repo
answer most likely just creates a harmless, orphaned project row (a `repo_key` that matches
nothing existing, so only this local repo ever posts to it) — but if it happens to coincidentally
match an already-registered `repo_key` (e.g. pasting a colleague's or unrelated project's HTTPS
URL), this repo's telemetry silently starts flowing into that other project, since there's no
authentication in the MVP to prevent it (server URL is the only access control). This is the same
class of risk as the case-sensitivity `repo_key` collision accepted above, just reachable via a
manual paste instead of a git-config quirk — not engineered around here.

See [US-2.2](2026-06-21-us-2.2-event-submission.md) for the consent notice `ripe init`
also prints.

**`ripe sync`** and any other command needing `projectId`:

1. If `.ripe/cache.json` has a cached `projectId`, use it directly
2. Otherwise, reads the current `origin` remote (prompting for the HTTPS equivalent if needed,
   same as `ripe init` step 2 above), resolves `projectId` via the server (posting the raw remote
   URL to `<server-url>/api/projects`, using `serverUrl` from `.ripe/settings.json`), and writes
   it back to `.ripe/cache.json`

**Recovery from a stale cache:** if the server rejects a cached `projectId`/`skillId` as unknown
(requires server-side validation — see [US-2.1](2026-06-21-us-2.1-skill-registration.md)/[US-2.2](2026-06-21-us-2.2-event-submission.md)),
`sync` fails, and — since the `SessionEnd` hook runs detached with no console to write to — the
advice ("delete `.ripe/cache.json` and run `ripe sync` again") is recorded in the local outcome
file and only surfaces at the *next* `ripe` invocation, never live when `sync` itself is
triggered. Deleting `.ripe/cache.json` alone is always sufficient and safe: it holds only
server-resolved state, so `.ripe/settings.json`'s `serverUrl` is untouched and no re-prompt is
needed. This is a manual stand-in for what a later slice can automate — same underlying
resolve-or-create calls, just triggered by hand instead of on rejection.

## Acceptance Criteria

Implementation lands in two iterations: **API first** (this iteration), then **CLI** (a later
iteration). Cases are grouped accordingly.

### API (done)

- Given no project exists whose normalized `repo_key` matches a given `remoteUrl`
  When `POST /api/projects` is called with `{name, remoteUrl}`
  Then it responds `201` with a new `projectId`
- Given a project already exists for that `repo_key`
  When `POST /api/projects` is called again with an equivalent `remoteUrl` (same or different
  `name`)
  Then it responds `200` with the same `projectId` — no `409`
- Given two different `remoteUrl`s share the same `name`
  When both are POSTed
  Then both succeed with distinct `projectId`s (`name` is no longer unique)
- Given a body missing `remoteUrl`
  When `POST /api/projects` is called
  Then it responds `400`
- Given a body missing `name`
  When `POST /api/projects` is called
  Then it responds `400` (unchanged)
- Given a `remoteUrl` that isn't `https://` (e.g. the common scp-like SSH form
  `git@github.com:org/repo.git`)
  When `POST /api/projects` is called
  Then it responds `400` — no project is created, no `repo_key`/`remote_url` is derived or
  persisted
- **Library invocation** (state assertion via direct DB read — `repo_key` isn't exposed on the
  wire, but its exact shape is a documented contract worth pinning. This one case exercises a
  non-default port, nested groups, and `.git`-suffix stripping all at once — behaviors
  `git-url-parse` itself already covers and tests upstream, so this proves we wire its output into
  `repo_key` correctly rather than re-testing the library's own coverage)
  Given a `remoteUrl` of `https://gitlab.com:2222/group/subgroup/repo.git`
  When `POST /api/projects` is called
  Then the persisted `repo_key` is exactly `gitlab.com/group/subgroup/repo`
- **`remote_url` normalization uses the unmangled host, and drops the port** (state assertion via
  direct DB read — proves `resource`, not `source`, is wired into `remote_url`; `source`'s
  subdomain-stripping heuristic is exactly the failure mode this guards against; this is the same
  real self-hosted host observed empirically during design, see `remote_url` Normalization above)
  Given a `remoteUrl` of `https://gitlab-forge.din.developpement-durable.gouv.fr:2222/org/repo.git`
  (a host `source` would mangle by stripping the `gitlab-forge.` prefix, but `resource` reports
  unmangled)
  When `POST /api/projects` is called
  Then the persisted `remote_url` is exactly
  `https://gitlab-forge.din.developpement-durable.gouv.fr/org/repo` — unmangled host, no `:2222`
- **Unparseable remote** (ours — how we react to a failed/empty parse is our logic, not the
  library's)
  Given a `remoteUrl` that isn't a valid git remote form (e.g. an empty string, or a string with
  no discoverable host/path)
  When POSTed
  Then it responds `400`, and no row (partial or otherwise) is written for either `repo_key` or
  `remote_url`

**Test strategy**: endpoint-level via `fastify.inject()` + a real in-memory `better-sqlite3` DB
(existing convention) — exercises migration → repository → use-case → endpoint together; no
mocking of internal layers. Deliberately does *not* re-test `git-url-parse`'s own
protocol-form/case/port/nested-group coverage — see "Behavioral over implementation-detail
assertions" in root `STANDARDS.md`.

### CLI (deferred to a later iteration)

- Given cwd is a git repo with an `https://` `origin` remote, when `ripe init` runs, then it reads
  the raw remote URL (no local normalization, no HTTPS prompt), prompts for `serverUrl`, POSTs
  `{name, remoteUrl}`, writes `.ripe/settings.json` (`{serverUrl}`) and `.ripe/cache.json`
  (`{projectId}`).
- Given cwd is a git repo with a non-`https://` `origin` remote (e.g. scp-like SSH), when
  `ripe init` runs, then it prompts the user for the HTTPS equivalent before proceeding, and
  POSTs `{name, remoteUrl}` using whatever the user typed — with no client-side validation of
  that answer.
- Given cwd has no `origin` remote, when `ripe init` runs, then it prints a clear error to stderr
  and returns `{status: 'error'}` (exit 1), without prompting for `serverUrl`.
- Given the server is unreachable, when `ripe init` runs, then it prints an error distinguishing
  "could not reach the server" and returns `{status: 'error'}`.
- Given the server responds `400` (an unparseable `remoteUrl`, a non-`https://` `remoteUrl` typed
  at the HTTPS prompt, or any other rejected `remoteUrl`), when `ripe init` runs, then it prints
  an error distinguishing "the server rejected this remote URL" — not the same message as the
  server-unreachable case — and returns `{status: 'error'}`.
- Given `ripe init` is run twice in the same repo, when the second run POSTs the same `remoteUrl`,
  then it gets the same `projectId` back with no confirmation prompt — and re-prompts for
  `serverUrl` both times (no short-circuit on existing local state).
- Given `.ripe/config.json` exists from old behavior, when `ripe init` runs, then it is never read
  or written — only `.ripe/settings.json`/`.ripe/cache.json` are used.
- Deleting a cached `projectId` and re-running `sync` re-resolves the same `projectId` via
  `repo_key` — no duplicate project is created (depends on `sync`, [US-2.2](2026-06-21-us-2.2-event-submission.md)).
- Deleting `.ripe/cache.json` and re-running `sync` recovers from a stale/rejected
  `projectId`/`skillId` without prompting for `serverUrl` again (depends on `sync`).
- The stale-cache recovery message is recorded in the local outcome file and surfaced only on the
  next `ripe` invocation, never printed live by the detached `sync` process (depends on `sync`).

**Test strategy**: command-level (`tests/commands/init.test.ts`), exercising `init` → `lib/` →
real filesystem → real git, with only the network layer intercepted by `nock` (existing
convention). Tests create a real tmp git repo (`git init`, `git remote add origin <url>`) rather
than injecting a fake remote-reader.

## Definition of Done

Beyond the automated acceptance criteria above, this manual check confirms `remote_url`'s actual
purpose — being a genuinely reachable, clonable address, not just a string in the expected
shape — since nothing in the automated suite makes a real network call. Not committed as an
automated test (would make CI depend on GitHub/GitLab/a French-government-hosted GitLab being
reachable); run by hand once before considering `remote_url` normalization done. Uses
`git ls-remote` rather than a full `git clone` — it proves the same "is this address reachable
and does it look like a real git remote" property without downloading repo contents.

For each `remoteUrl` below, `POST /api/projects` (or call `Project.create` directly), read back
the persisted `remote_url`, and confirm `git ls-remote <that remote_url>` succeeds and returns at
least a `HEAD` ref. All four were verified reachable during design (2026-08-02):

| Input `remoteUrl` | Expected `remote_url` |
| --- | --- |
| `https://github.com/octocat/Hello-World.git` | `https://github.com/octocat/Hello-World` |
| `https://gitlab.com/gitlab-org/gitlab-test.git` | `https://gitlab.com/gitlab-org/gitlab-test` |
| `https://codeberg.org/forgejo/forgejo.git` | `https://codeberg.org/forgejo/forgejo` |
| `https://gitlab-forge.din.developpement-durable.gouv.fr/snum/pnm2/dihal/chrs-group/chrs.git` | `https://gitlab-forge.din.developpement-durable.gouv.fr/snum/pnm2/dihal/chrs-group/chrs` |

The last row is the one that matters most: it's a real self-hosted GitLab instance whose SSH
access goes through a dedicated `ssh.*`-prefixed subdomain distinct from its web/HTTPS host
(confirmed empirically: `https://ssh.gitlab-forge.din.developpement-durable.gouv.fr/...` — the
naive result of reusing a `source`-style or SSH-literal host — fails to connect at all, while the
`resource`-derived host above succeeds). This is the concrete case that justifies both the
`resource`-over-`source` choice and the current HTTPS-only restriction (see "`remote_url`
Normalization" and the HTTPS-only bullet in Scope) — losing this manual check would risk silently
reintroducing the same host-mangling bug in a future change.
