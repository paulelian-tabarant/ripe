# US-1.3 — Remote-Derived Project Identity

**Slice**: 1 — Foundation & Project Registration
**Status**: Ready for planning

## User Story

As a developer, running `ripe init` on a project I've already registered (or that a teammate
already registered) just works — no manual confirmation, no committed config file, no risk of
silently attaching to the wrong project.

## Context

[US-1.1](2026-06-21-us-1.1-project-registration.md) keyed project uniqueness on the directory
name and required a committed `.ripe/config.json` so team members could share the same
`project_id`. This user story supersedes that behavior per [ADR-018](../../architecture/decisions/ADR-018-remote-derived-project-identity.md)
— US-1.1 itself is shipped and stays as a historical record; this story describes the new
behavior that replaces it.

Project identity moves to a canonicalized `origin` git remote URL (`repo_key`). Local state splits
into two gitignored files: `.ripe/settings.json`, holding only the interactively-configured
`serverUrl` (unchanged from US-1.1); and `.ripe/cache.json`, holding everything server-resolved or
derived — `project_id`, the skill ID cache introduced by [US-2.1](2026-06-21-us-2.1-skill-registration.md)
(itself not yet shipped), and `last_synced_sha` (for a future slice). `.ripe/config.json` is
retired — nothing in either new file is committed.

## Scope

**In scope:**

- `repo_key` column (`UNIQUE`) on the `projects` table; `name` becomes a non-unique display field
- `POST /api/projects` becomes find-or-create on `repo_key` (idempotent, no 409/confirmation flow)
- CLI derives `repo_key` from `git remote get-url origin`, normalizing SSH/HTTPS forms to
  `host/org/repo`
- No `origin` remote → hard error, no fallback to directory name
- `project_id` may be cached locally (gitignored) as a call-skipping optimization, never committed
  — a missing/stale cache entry just triggers a re-resolve via `repo_key`, no ambiguity
- Local state splits into `.ripe/settings.json` (gitignored: `serverUrl` only, interactively set
  by `ripe init`) and `.ripe/cache.json` (gitignored: `project_id` cache, skill ID cache, and any
  other server-resolved/derived state introduced by later slices, e.g. `last_synced_sha`)
- `.ripe/config.json` retired

**Out of scope:**

- Forks (naturally register as separate projects — no special handling)
- Repository rename/move detection (same accepted limitation as V1 skill rename)
- Multiple remotes beyond `origin`
- Automatic recovery when the server rejects a cached `project_id`/`skill_id` as unknown (e.g.
  after manual server-side data loss) — see "Recovery from a stale cache" below; automating it is
  deferred to a later slice

## API Contracts

```text
POST /api/projects
Body: { name: string, repoKey: string }
→ 201 { "projectId": "proj_<nanoid>" }                          (new project)
→ 200 { "projectId": "proj_<nanoid>" }                          (existing repoKey, idempotent)
→ 400                                                            (invalid body, e.g. missing repoKey)
```

`repo_key` is `UNIQUE` on the server (DB column; the wire field is `repoKey`); `name` is stored but
not constrained. No 409 case remains — the same `repo_key` always resolves to the same `projectId`
without confirmation.

## CLI Behavior

**`ripe init`:**

1. Reads `origin` remote via `git remote get-url origin`; no remote → stderr error, exit 1
2. Normalizes the remote URL to `repo_key` (`host/org/repo`, stripping protocol/user/`.git` suffix)
3. Reads project display name from the current working directory (unchanged from US-1.1)
4. POSTs `{ name, repoKey }` to `<server-url>/api/projects`
5. Server unreachable → stderr error, exit 1
6. Writes `serverUrl` to `.ripe/settings.json` (unchanged from US-1.1 — still interactively
   prompted; the only field in local state that isn't server-resolved or git-derived), and the
   returned `projectId` to `.ripe/cache.json`

See [US-2.2](2026-06-21-us-2.2-event-submission.md) for the consent notice `ripe init`
also prints.

**`ripe sync`** and any other command needing `projectId`:

1. If `.ripe/cache.json` has a cached `projectId`, use it directly
2. Otherwise, recomputes `repo_key` from the current `origin` remote, resolves `projectId` via
   the server (using `serverUrl` from `.ripe/settings.json`), and writes it back to `.ripe/cache.json`

**Recovery from a stale cache:** if the server rejects a cached `projectId`/`skillId` as unknown
(requires server-side validation — see [US-2.1](2026-06-21-us-2.1-skill-registration.md)/[US-2.2](2026-06-21-us-2.2-event-submission.md)),
`sync` fails, and — since the `SessionEnd` hook runs detached with no console to write to — the
advice ("delete `.ripe/cache.json` and run `ripe sync` again") is recorded in the local outcome
file and only surfaces at the *next* `ripe` invocation, never live when `sync` itself is
triggered. Deleting `.ripe/cache.json` alone is always sufficient and safe: it holds only
server-resolved state, so `.ripe/settings.json`'s `serverUrl` is untouched and no re-prompt is
needed. This is a manual stand-in for what a later slice can automate — same underlying
resolve-or-create calls, just triggered by hand instead of on rejection.

## Acceptance Criteria

- [ ] `ripe init` in a repo with no `origin` remote exits 1 with a clear error
- [ ] `ripe init` normalizes SSH (`git@host:org/repo.git`), `ssh://` and HTTPS remote forms to the
      same `repo_key`
- [ ] Two developers on the same repo (different clone protocols) resolve to the same `projectId`
      without any prompt
- [ ] `POST /api/projects` with an already-known `repo_key` returns the existing `projectId`
      idempotently — no 409
- [ ] `.ripe/config.json` is no longer created or read by any command
- [ ] `.ripe/settings.json` holds `serverUrl`
- [ ] `.ripe/cache.json` holds a cached `projectId` (reserved to also hold the skill ID cache once
      [US-2.1](2026-06-21-us-2.1-skill-registration.md) ships)
- [ ] Deleting a cached `projectId` and re-running `sync` re-resolves the same `projectId` via
      `repo_key` — no duplicate project is created
- [ ] A project's directory name is stored as a non-unique display field, not used for identity
- [ ] Deleting `.ripe/cache.json` and re-running `sync` recovers from a stale/rejected
      `projectId`/`skillId` without prompting for `serverUrl` again
- [ ] The stale-cache recovery message is recorded in the local outcome file and surfaced only on
      the next `ripe` invocation, never printed live by the detached `sync` process
