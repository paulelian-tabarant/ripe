# US-2.1 — Skill Registration

**Slice**: 3 — Core Pipeline  
**Status**: Ready for planning

As the telemetry system, committed skills in `.claude/skills/` are registered with the server,
with their assigned IDs cached locally to avoid redundant registration calls.

## Context

Skill registration happens in two places:

1. **`ripe init`**: registers all committed skills from main branch (initial setup)
2. **`ripe sync` Phase 1**: registers new committed skills not yet on server (ongoing)

Only skills **committed on main branch** are tracked — uncommitted files and skills only on
feature branches are ignored, even if invoked. Skill IDs are cached in `.ripe/skills.json`
(gitignored, local-only). The cache is a call-skipping optimization, not a source of truth:
the server is idempotent on `(project_id, name)` (ADR-015), so a lost or absent cache just means
the next `init`/`sync` re-POSTs already-known skills and gets the same `skill_id`s back — no
duplicates are ever created. Skills are project-scoped: `(project_id, name)` uniquely identifies
a skill.

**Rename handling:** V2 feature, using git's own rename detection against a locally-tracked
`last_synced_sha` rather than the skills cache — see [version-2-scope.md](../versions/version-2-scope.md#feature-skill-rename-detection).
In V1, renaming = delete + add (orphans historical data).

**Detached execution:** `ripe sync` (Phase 1 below), when invoked by the `SessionEnd` hook, runs
detached from the parent process per [ADR-001](../../architecture/decisions/ADR-001-sessionend-hook-transcript-parsing.md)
— the hook returns immediately, so there is no terminal left to write "stderr warning" to during
Phase 1. Non-fatal issues below are recorded in the local outcome file instead and surfaced by the
next `ripe` invocation, not printed live. `ripe init` is a direct, blocking command (a developer
runs it and waits), so its own stderr output is unaffected.

## Scope

**In scope:**

- `POST /api/skills` server endpoint
- `ripe init`: register committed skills from main branch
- Phase 1 of `ripe sync`: register new committed skills
- Gitignored, local cache file `.ripe/skills.json` with `(name → skill_id)` mappings
- Skip uncommitted and namespaced skills

**Out of scope:**

- Skill deletion or archival
- Rename detection (V2)
- Skills from directories other than `.claude/skills/`
- Tracking uncommitted/WIP skills

## API Contract

```text
POST /api/skills
Body: {
  project_id: string,
  skills: Array<{ name: string }>
}
→ 200 {
  skills: Array<{ name: string, skill_id: string }>
}
```

Server behavior: `ON CONFLICT(project_id, name) DO NOTHING` — same `(project_id, name)` always
returns the same `skill_id`. Only skills absent from the local cache are sent.

## Client Behavior

**`ripe init`:**

0. If `.ripe/config.json` does not exist: exit 0 silently (project not initialized via `ripe init`)
1. Scans `.claude/skills/` on main branch for committed skills
2. Skips namespaced skills (containing `:`) — stderr warning
3. POSTs all skills to `POST /api/skills`
4. Writes returned `skill_id`s to `.ripe/skills.json` (gitignored, local file)
5. Server unreachable → stderr error, exit 1 (blocks init)

**Phase 1 of `ripe sync`** (runs inside the detached process, see above):

1. Scans `.claude/skills/` for skills committed on main branch only
2. Skips uncommitted files and skills only on feature branches — recorded in the local outcome
   file: "skill X not on main, skipping"
3. Skips namespaced skills (containing `:`) — recorded in the local outcome file
4. For skills absent from `.ripe/skills.json`, POSTs to `POST /api/skills`
5. Writes returned `skill_id`s to `.ripe/skills.json`
6. Server unreachable → failure recorded in the local outcome file, exits 0 (non-blocking); next
   `ripe` invocation surfaces the failure

## Acceptance Criteria

- [ ] `ripe init` registers all skills committed on main branch
- [ ] `ripe sync` registers new skills committed on main, not in `.ripe/skills.json`
- [ ] Uncommitted skills and skills only on feature branches are skipped, recorded in the local
      outcome file during `sync` (not printed live — `sync` runs detached)
- [ ] Skill IDs are written to `.ripe/skills.json` (gitignored, local file)
- [ ] Already-cached skills are not included in POST payload
- [ ] Same `(project_id, name)` always returns same `skill_id` (server idempotency)
- [ ] Namespaced skills (containing `:`) are skipped, recorded in the local outcome file during `sync`
- [ ] Server unreachable during `init` → stderr error, exit 1 (blocking command, direct feedback)
- [ ] Server unreachable during `sync` → recorded in the local outcome file, exit 0, surfaced on
      the next `ripe` invocation
- [ ] Empty `.claude/skills/` → no POST made
- [ ] `ripe sync` (Phase 1 + Phase 2) runs in a detached child process; the parent returns
      near-instantly regardless of network conditions
