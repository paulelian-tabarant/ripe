# US-2.1 — Skill Registration

**Slice**: 3 — Core Pipeline  
**Status**: Ready for planning

As the telemetry system, committed skills in `.claude/skills/` are registered with the server via
`ripe init`, with their assigned IDs cached locally to avoid redundant registration calls.

## Context

`ripe init` eagerly registers the full current catalog of committed-on-main skills, so the
server's skill list is complete even for skills never yet invoked. This is a direct, blocking
command — a developer runs it and waits — so its own stderr output is unaffected by any of the
detached-execution concerns that apply to `ripe sync` (see [US-2.2](2026-06-21-us-2.2-event-submission.md),
which introduces `ripe sync` and reuses the endpoint and cache format defined here for its own,
separately-specified lazy skill resolution).

Only skills **committed on main branch** are tracked — uncommitted files and skills only on
feature branches are ignored. Skill IDs are cached in `.ripe/cache.json` (gitignored, local-only,
shared with the project ID cache per [US-1.3](2026-07-25-us-1.3-remote-derived-project-identity.md)).
The cache is a call-skipping optimization, not a source of truth: the server is idempotent on
`(project_id, name)` (ADR-015), so a lost or absent cache just means the next `init` re-POSTs
already-known skills and gets the same `skill_id`s back — no duplicates are ever created. Skills
are project-scoped: `(project_id, name)` uniquely identifies a skill.

**v1 skill lifecycle scope is addition only.** There's no "modification" concept — identity is by
name alone, so a skill's `skill_id` never changes as long as its name doesn't, regardless of
content changes. Removal/archival is explicitly out of scope (below): a skill deleted from
`.claude/skills/` can no longer be invoked, so its cache entry is simply never looked up again —
harmless, no cleanup needed.

**Rename handling:** V2 feature, using git's own rename detection against a locally-tracked
`last_synced_sha` rather than the skills cache — see [version-2-scope.md](../versions/version-2-scope.md#feature-skill-rename-detection).
In V1, renaming = delete + add (orphans historical data).

## Scope

**In scope:**

- `POST /api/skills` server endpoint, validating `project_id` exists
- `ripe init`: eagerly register the full committed-on-main skill catalog
- Skill ID cache lives in `.ripe/cache.json` (gitignored, shared with the project ID cache) as
  `(name → skill_id)` mappings
- Skip namespaced skills

**Out of scope:**

- Skill deletion or archival
- Rename detection (V2)
- Skills from directories other than `.claude/skills/`
- Tracking uncommitted/WIP skills
- `ripe sync`'s own (lazy, invocation-triggered) skill resolution — see [US-2.2](2026-06-21-us-2.2-event-submission.md)

## API Contract

```text
POST /api/skills
Body: {
  projectId: string,
  skills: Array<{ name: string }>          (name required, non-empty; extra fields ignored)
}
→ 200 Array<{ name: string, skillId: string }>            (including [] for an empty request)
→ 400                                                     (unknown projectId, or a skills item missing/empty name)
→ 422                                                     (duplicate names within the same skills array)
```

Server behavior: `ON CONFLICT(project_id, name) DO NOTHING` — same `(project_id, name)` always
returns the same `skill_id`. The client only calls this endpoint when its scanned skill-name set
differs from what's cached (see Client Behavior); when it does call, it sends the full scanned
catalog, not just the delta — the server's idempotency makes re-sending already-known names free,
and it keeps the client's cache-merge logic a plain overwrite instead of an incremental patch.

No race-condition handling for concurrent identical-name registrations: `better-sqlite3` calls are
synchronous and this is a single-instance deployment, so a request's check-then-insert can't be
interleaved by another request in the same process — same non-issue as `RegisterProject` today.

## Client Behavior

**`ripe init`:**

1. Resolves the git ref to scan: local `main`, falling back to `origin/main` if absent; stderr
   error + exit 1 if neither exists.
2. Scans `.claude/skills/*/SKILL.md` committed on that ref (via `git ls-tree` + `git show` — the
   working tree/current branch is never read directly, so this works regardless of what's checked
   out). A skill's name is its SKILL.md frontmatter `name:` field, not its directory name.
3. Skips a skill if its name contains `:` (namespaced) or its frontmatter is missing/malformed
   (no `name` field) — either way, stderr warning, keeps scanning the rest.
4. No skills found (`.claude/skills/` empty or absent on the resolved ref) → stderr warning, no
   POST made.
5. Compares the scanned name set to `.ripe/cache.json`'s cached `skillIds` keys. Identical → no
   POST made. Different → POSTs the full scanned catalog to `POST /api/skills`.
6. On success, the response's `{name, skillId}` list replaces `.ripe/cache.json`'s `skillIds` map
   wholesale (gitignored, shared with the project ID cache).
7. Server unreachable → stderr error, exit 1 (blocks init) — but anything already written earlier
   in the run (e.g. project registration's settings/cache) stays on disk, since writes happen
   sequentially as each step succeeds.

## Acceptance Criteria

**API — `POST /api/skills`**

- Given a registered project with no skills yet
  When `POST /api/skills` is called with `projectId` and a list of new skill names
  Then it returns 200 with a `skillId` for each name
- Given skill names already registered for a project
  When `POST /api/skills` is called again with the same names
  Then the response returns the same `skillId`s, no duplicate rows are created
- Given a request mixing already-registered and brand-new names
  When `POST /api/skills` is called
  Then existing names keep their `skillId`, new names get freshly assigned ones, all in one
  response
- Given an unknown `projectId`
  When `POST /api/skills` is called
  Then it returns 400
- Given a `skills` array item with a missing or empty `name` (extra fields on the item are not
  validated away)
  When `POST /api/skills` is called
  Then it returns 400
- Given a `skills` array containing duplicate names
  When `POST /api/skills` is called
  Then it returns 422
- Given a registered project and an empty `skills: []` array
  When `POST /api/skills` is called
  Then it returns 200 with `[]`

**CLI — `ripe init` skill registration**

- Given skills committed on main with valid frontmatter, and an empty cache
  When `ripe init` runs
  Then the full scanned catalog is POSTed to `/api/skills` and the response's `skillId`s replace
  `.ripe/cache.json`'s `skillIds` map, alongside `projectId`
- Given the scanned skill-name set is identical to the cached `skillIds` keys
  When `ripe init` runs again
  Then no `POST /api/skills` call is made at all
- Given `.claude/skills/` is empty or absent on the resolved ref
  When `ripe init` runs
  Then no `POST /api/skills` call is made, and a stderr warning is printed noting no skills were
  found
- Given a skill set up to be skipped for reason `<reason>` (namespaced `name:` containing `:`,
  missing/malformed frontmatter, or committed only on a feature branch / left uncommitted)
  When `ripe init` runs
  Then that skill is excluded from the POST body and absent from the cache — the two warn-worthy
  reasons (namespaced, malformed) additionally print a stderr warning; "not on main" doesn't
- Given no local `main` branch but `origin/main` exists
  When `ripe init` runs
  Then it still registers main's committed skills, reading from `origin/main`
- Given neither local `main` nor `origin/main` exists
  When `ripe init` runs
  Then stderr error, exit 1, no POST made
