# US-1.3 — Remote-Derived Project Identity: CLI — Implementation Plan

**Status**: Approved, not yet implemented.

## Context

The API slice of US-1.3 (server-managed `repo_key`/`remote_url`, HTTPS enforcement) is done and
merged to `main`. This branch (`feat/cli/1-3-split-settings-and-cache-in-client`) covers the last
remaining CLI slice, per the story doc's "CLI (deferred to a later iteration)" acceptance criteria
and the "Open items for the CLI iteration" section of
`docs/_plans/2026-08-01-us-1.3-remote-derived-project-identity-api.md`:

- Retire `.ripe/config.json` (a single, committed file) in favor of two **gitignored** files:
  `.ripe/settings.json` (`{serverUrl}`, interactively set) and `.ripe/cache.json`
  (`{projectId}`, server-resolved).
- Drop the short-circuit on re-`init` (the "`.ripe/config.json` already exists" early return) —
  the API is now idempotent (find-or-create on `repo_key`, no `409`), so re-running `init` should
  just re-resolve and re-write, not warn-and-exit.
  - **Refinement agreed with the user, deviating from the story doc's original wording**
    ("re-prompts for `serverUrl` both times, no short-circuit"): instead of always blindly
    re-prompting, if `.ripe/settings.json` already has a `serverUrl`, tell the user what was found
    and ask whether to keep it or enter a new one. Keep → skip the URL prompt loop entirely and use
    the cached value. Enter new → go through the normal validate-until-valid loop, same as when no
    settings file exists. This still satisfies "no short-circuit on the registration/write path"
    (registration always re-runs, local state is always rewritten) while avoiding a pointless
    re-prompt for unchanged input. The story doc is updated to match as part of this plan (see
    "Docs/config touch-ups" below).
- Drop the stale US-1.1-era "attach to existing project?" confirmation prompt — dead UX now that
  there's no `409`/conflict case to confirm.

This is pure CLI local-state plumbing; it doesn't touch identity resolution, `getRemoteUrl`, or
`registerProject`'s HTTPS-prompt/error-distinction logic (all already shipped and correct).

## Source changes

**`cli/src/lib/writeConfig.ts` → replaced by two files**, mirroring the existing
`writeConfig`/`readConfig` shape but split by concern:

- `cli/src/lib/writeSettings.ts`: `export interface RipeSettings { serverUrl: string }` +
  `writeSettings(settingsPath, settings)` — same `mkdirSync`+`writeFileSync` body as today's
  `writeConfig`.
- `cli/src/lib/writeCache.ts`: `export interface RipeCache { projectId: string }` +
  `writeCache(cachePath, cache)` — same shape.

**`cli/src/lib/readConfig.ts` — deleted**, replaced by a narrower **`cli/src/lib/readSettings.ts`**:
`export function readSettings(settingsPath: string): RipeSettings | undefined` — same
exists/parse/validate shape as today's `readConfig`, but only checks for `serverUrl` (mirrors
`RipeSettings` from `writeSettings.ts`). `.ripe/cache.json` is never read by `init` (nothing to
reuse — `projectId` always comes fresh from the registration call); a future `sync` command reads
it, per the story's "`ripe sync`" section, out of scope here.

**`cli/src/commands/init.ts`** (`init.ts:23-74`):

- Remove the `configPath`/`existing = readConfig(...)` block entirely (`init.ts:28-37`) — no
  short-circuit on the registration path.
- Remove `InitOptions.promptFn` and the `useExisting`/"Attach to it?" branch (`init.ts:60-67`) —
  always write local state and print a message, whether `result.created` is `true` or `false`
  (message distinction kept, see below).
- **New**: before the `serverUrl` prompt loop, call `readSettings(settingsPath)`. If it returns an
  existing `serverUrl`, call a new injectable `confirmServerUrlPromptFn(existingUrl): Promise<boolean>`
  (default: `` Found existing server URL: "<url>". Keep it? (y/n) `` via the shared `ask()` helper,
  same y/n parsing as the old `defaultPromptFn`). If confirmed, use that `serverUrl` directly and
  skip the validate-until-valid loop entirely. If declined (or no existing settings), fall through
  to the existing `while (true) { serverUrl = await urlPromptFn(); ... }` loop unchanged.
- Replace the single `writeConfig(configPath, {...})` call with `writeSettings(settingsPath,
  {serverUrl})` + `writeCache(cachePath, {projectId: result.projectId})`, using two paths:
  `join(currentDirectoryName, '.ripe/settings.json')` and `join(currentDirectoryName,
  '.ripe/cache.json')` — always rewritten, even when `serverUrl` was reused unchanged (registration
  itself is never short-circuited).
- Keep the `created` ? "Project registered: X" : "Using existing project ID: X" message
  distinction (still useful signal, just no longer gates a prompt).
- `defaultPromptFn` helper (`init.ts:143-147`) is repurposed/renamed into
  `defaultConfirmServerUrlPromptFn` for the new keep/update prompt, rather than deleted outright.

**`cli/src/cli.ts`**: update the `init` help text (currently "write .ripe/config.json") to mention
the new files.

## Test changes (`cli/tests/commands/init.test.ts`)

- Remove the `.ripe/config.json already exists` test and the `it.each` "re-registers when
  .ripe/config.json %s" block (config.json is no longer read at all — these test a code path that
  no longer exists).
- Remove the old `promptFn`-driven tests ("writes config and exits 0 on 200 when user confirms" /
  "exits 0 without writing config on 200 when user declines") — that confirmation no longer
  exists. Replace with a plain test asserting a `200` (existing project) response still writes
  settings+cache and succeeds, printing the "Using existing project ID" message, with no
  confirmation prompt involved.
- **New tests for the keep/update `serverUrl` behavior**:
  - Given `.ripe/settings.json` already has a `serverUrl` and the user confirms keeping it, `init`
    never calls `urlPromptFn`, reuses the existing `serverUrl` for both the write and (implicitly)
    nothing else, and still writes settings+cache.
  - Given `.ripe/settings.json` already has a `serverUrl` but the user declines, `init` falls
    through to the normal `urlPromptFn` loop and writes the newly-entered `serverUrl`.
  - Given no `.ripe/settings.json` exists yet, `confirmServerUrlPromptFn` is never called (nothing
    to confirm) and `init` goes straight to `urlPromptFn`.
- Update `readWrittenConfig()`/`writeExistingConfig()` helpers to read/write
  `.ripe/settings.json` + `.ripe/cache.json` separately (two small helpers instead of one), and
  update all assertions (`config.projectId`/`config.serverUrl`) to read from the right file.
- No dedicated test for "stray `.ripe/config.json` is ignored" — that's a migration note (old
  users can delete the file by hand), not product behavior worth pinning in an automated test;
  it falls out naturally from `readConfig.ts` being deleted and no code path referencing
  `config.json` anymore.
- Everything else (HTTPS prompt tests, no-remote test, unreachable/400 error-message tests,
  invalid-URL retry loop) is unaffected by this split and stays as-is.
