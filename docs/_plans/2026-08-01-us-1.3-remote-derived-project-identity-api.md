# US-1.3 — Remote-Derived Project Identity: API — Implementation Plan

**Status**: Approved, not yet implemented.

## Context

`docs/spec/user-stories/2026-07-25-us-1.3-remote-derived-project-identity.md` (see its
"Acceptance Criteria" → "API (this iteration)" section) supersedes US-1.1's name-based project
uniqueness with a `repo_key` derived from the project's git `origin` remote. Per
[ADR-018](../architecture/decisions/ADR-018-remote-derived-project-identity.md), normalization is
**server-side**: the client sends the raw remote URL (`remoteUrl`), and the API computes and owns
`repo_key`.

This plan covers the **API slice only** — CLI changes (deriving nothing client-side, just
forwarding the raw remote, splitting `.ripe/config.json` into `settings.json`/`cache.json`) are a
separate, later iteration (see the doc's "CLI (deferred to a later iteration)" section).

## Dependency: `git-url-parse`

Adding `git-url-parse` (`^16.1.0`) to `api/`'s dependencies rather than hand-rolling protocol
parsing. It handles scp-like SSH (`git@host:org/repo.git`), `ssh://`, `https://`, and `git://`
forms uniformly, exposes `source` (host, no port) and `owner`/`name` (which correctly preserve
GitLab-style nested subgroups — verified against its own test suite), and a `git_suffix` flag for
`.git` stripping. Ships its own types (`./lib/index.d.ts`) — no `@types/` package needed.
~5.85M weekly downloads, actively maintained (releases through 2025, not archived).

Our own code is a thin wrapper: validate the parse produced a non-empty host+path, then join
`${source}/${owner}/${name}` — no case transformation on top of the library's output. This is
deliberate: the library already lowercases `source` for `https://`/`ssh://` (via WHATWG `URL`,
per-spec for DNS hostnames), but never touches `owner`/`name`, which may be case-sensitive
identifiers on a self-hosted git server's filesystem. We trust that judgment rather than
independently lowercasing paths ourselves.

## Files

1. **`api/package.json`** — add `"git-url-parse": "^16.1.0"` to `dependencies`.

2. **`api/src/db/migrations.ts`** — new migration (version 2):
   - Since `name`'s `UNIQUE` constraint is defined inline in the `CREATE TABLE` and SQLite can't
     drop a column constraint via `ALTER TABLE`, rebuild the table: create `projects_new` with
     `id TEXT PRIMARY KEY, name TEXT NOT NULL, repo_key TEXT NOT NULL UNIQUE`, copy existing rows,
     drop `projects`, rename `projects_new` → `projects`.
   - **Confirmed with the user (not just assumed)**: production has no registered projects yet,
     so there's nothing to backfill — `repo_key` can go straight to `NOT NULL UNIQUE` with no
     migration path for pre-existing rows. This is a one-way door: unlike a typical
     nullable→backfill→`NOT NULL` column rollout (see e.g. the event-schema-evolution precedent),
     there's no way to backfill `repo_key` for a real pre-existing row after the fact — the
     original remote URL was never stored, only `name`. If this migration ever needs to run
     against a database with real rows, it needs a different strategy first (this plan doesn't
     cover that case).
   - `down`: reverse (rebuild dropping `repo_key`, restoring `UNIQUE` on `name`).

3. **`api/src/lib/normalizeRepoKey.ts`** (new)
   - `export function normalizeRepoKey(remoteUrl: string): string | undefined`
   - Uses `GitUrlParse(remoteUrl)`; wrapped in `try/catch` in case the library throws on
     unparseable input (behavior undocumented — defensive).
   - Returns `undefined` if `source`, `owner`, or `name` end up empty/missing, or on a caught
     exception — the "expected failure" result-object pattern, not a throw.
   - On success: `` `${source}/${owner}/${name}` `` (no `.toLowerCase()` — see "Dependency"
     section above for why).

4. **`api/src/repositories/ProjectRepository.ts`**
   - `Project` type gains `repoKey: string` (domain-shaped — DB column `repo_key` stays internal
     to the repository, per "no DB details leaking into use-cases").
   - Replace `getByName`/`findByNameStatement` with `getByRepoKey(repoKey: string): Project | undefined`.
   - `addNewProject` takes `{ id, name, repoKey }`, inserts all three columns.
   - `findAllStatement`/`list()` unchanged in shape (`{ id, name }` — `repo_key` not needed by
     `ListProjects`, so `list()`'s `SELECT` can stay `id, name` or select `repo_key` too and just
     not expose it; simplest is to leave `list()`'s query as-is).

5. **`api/src/contracts/projects.ts`**
   - `RegisterProjectRequestBody`: `{ name: string; remoteUrl: string }` (drop the old bare
     `{ name }`).
   - Drop `ProjectConflictResponseBody` (no more `409`).
   - `RegisterProjectResponseBody` unchanged (`{ projectId: string }`).

6. **`api/src/use-cases/RegisterProject.ts`**
   - New: `export class InvalidRemoteUrlError extends Error` — constructed with the original
     `remoteUrl`, message like `` `Could not derive a repo_key from remoteUrl: ${remoteUrl}` ``,
     `this.name = 'InvalidRemoteUrlError'`. Returned as a value, never thrown — consistent with
     this repo's "result objects over thrown errors for expected failures" rule; the `Error`
     shape is used here for its `.message`/`instanceof` ergonomics, not to signal an exception.
   - `RegisterProjectResult` becomes `{ created: boolean; projectId: string } | InvalidRemoteUrlError`
     (a discriminated union via `instanceof`, not a boolean flag).
   - `run(name: string, remoteUrl: string): RegisterProjectResult`:
     - `normalizeRepoKey(remoteUrl)` → if `undefined`, `return new InvalidRemoteUrlError(remoteUrl)`.
       (`normalizeRepoKey` itself is unchanged — stays a minimal `string | undefined` parsing
       helper, matching `getByRepoKey`'s existing idiom; `run` already has `remoteUrl` in scope,
       so constructing the named error here loses no context and keeps the parsing utility free
       of error-vocabulary concerns.)
     - `getByRepoKey(repoKey)` → `{ created: false, projectId: existing.id }` if found; otherwise
       `addNewProject({ id: proj_<nanoid>, name, repoKey })` → `{ created: true, projectId }`.

7. **`api/src/endpoints/projectEndpoints.ts`**
   - `projectSchema` requires both `name` and `remoteUrl` (non-empty strings) — trivial
     presence/shape checks stay here, never in the use-case.
   - Handler: `const result = opts.registerProject.run(request.body.name, request.body.remoteUrl)`.
     - `result instanceof InvalidRemoteUrlError` → `reply.code(400).send({ message: result.message })`.
     - `result.created` → `201`.
     - otherwise → `200` (not `409`) — same `RegisterProjectResponseBody` shape.
   - Remove the `ProjectConflictResponseBody` import/branch entirely.

8. **Tests**
   - `api/tests/helpers/postProjects.ts` — `RegisterProjectRequestBody` now requires `remoteUrl`;
     update the `Partial<...>` signature accordingly (no other change needed).
   - `api/tests/endpoints/registerProject.test.ts` — rewrite around the new contract. No separate
     `repoKeyNormalization.test.ts` file, and no isolated unit test for `normalizeRepoKey` — with
     just 2 normalization-specific cases, there's no speed/isolation benefit to a fine-grained
     test per root `STANDARDS.md`'s "coarse-grained over fine-grained" default, so both are added
     directly here, exercised through the full endpoint stack like everything else in this file:
     - `201` + new `projectId` for a fresh `remoteUrl`.
     - `200` (not `409`) + same `projectId` for a repeat of an equivalent `remoteUrl`.
     - two different `remoteUrl`s sharing the same `name` both succeed with distinct `projectId`s.
     - `400` for missing `remoteUrl`, missing `name`, empty `name`.
     - `400` for an unparseable `remoteUrl` (e.g. `''`, `'not a url'`) — ours to react to, not the
       library's, so it's a dedicated case.
     - **Library invocation**: one state assertion (direct DB read, since `repo_key` isn't exposed
       on the wire) for `ssh://git@gitlab.com:2222/group/subgroup/repo.git` →
       `gitlab.com/group/subgroup/repo` — exercises `ssh://` parsing, port dropping, nested
       groups, and `.git` stripping all at once, proving the library's output is wired into
       `repo_key` correctly. Deliberately one case, not one per equivalence class — `git-url-parse`
       already covers and tests those forms upstream, per the "Behavioral over
       implementation-detail assertions" rule.
   - `api/tests/endpoints/listProjects.test.ts` — check whether it constructs request bodies with
     the old `{ name }` shape (via `postProjects` or inline); if so, add `remoteUrl` to keep it
     registering projects successfully. No behavior change to `GET /api/projects` itself.

## Not in scope (this iteration)

- `ripe sync`, skill ID cache, `last_synced_sha` — later slices (US-2.1/US-2.2).

## Verification

- `pnpm --filter api ci:checks` (lint + typecheck + test) must pass.
- Manually: `curl -X POST http://localhost:<port>/api/projects -d '{"name":"x","remoteUrl":"git@github.com:org/repo.git"}'`

## Execution notes

Single cohesive change (migration → repository → normalization lib → use-case → endpoint →
contracts → tests, all interdependent) — one implementer, no parallel subtask split.

**TDD, red-green-refactor, per slice:**

1. Migration (`repo_key` column, `name` no longer unique) — no direct test of the migration
   itself; its correctness is exercised indirectly by the endpoint tests that follow.
2. `normalizeRepoKey` and `ProjectRepository.getByRepoKey`/`addNewProject` — no isolated unit
   tests for either; both are exercised through the endpoint tests below (this repo doesn't
   unit-test repositories in isolation currently, and with only 2 normalization-specific cases
   there's no isolation/speed benefit to a fine-grained test either — see "Tests" above).
3. `RegisterProject.run` + `POST /api/projects` — failing acceptance tests first, covering every
   case from "Tests" above (new/existing/name-not-unique/missing-field/unparseable/library
   invocation), simplest implementation, green, refactor. If the library-invocation or
   unparseable-remote case fails, fix `normalizeRepoKey`, not the endpoint.

## Open items for the CLI iteration (not blocking this one)

- CLI reads `git remote get-url origin`, forwards the raw string as `remoteUrl` — no local
  normalization.
- `.ripe/config.json` retired; `.ripe/settings.json` (`serverUrl`) / `.ripe/cache.json`
  (`projectId`) introduced.
- No short-circuit on re-`init` — always re-prompts and re-POSTs, relying on server idempotency.
