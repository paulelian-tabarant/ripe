# US-2.1 — Skill Registration — Implementation Plan

**Status**: Approved, not yet implemented.

## Context

`docs/spec/user-stories/2026-06-21-us-2.1-skill-registration.md` (Acceptance Criteria are the
source of truth for test cases) + [ADR-021](../architecture/decisions/ADR-021-project-skill-aggregate.md)
(`Skill` is a child entity of the `Project` aggregate, not a peer with its own repository).

Route is `POST /api/projects/:id/skills` (404 on unknown project id), not the originally-drafted
`POST /api/skills` with `projectId` in the body — nesting under `/projects/:id` matches the
aggregate boundary and drops a redundant body field. `ripe init` requires a local `main` branch
and fails loudly if absent (no `origin/main` fallback — this always runs in a developer's local
environment, not CI).

Both `api/` and `cli/` went through unrelated structural refactors after this story's design was
first discussed (kebab-case filenames; `api/src/core/{domain,use-cases}` and
`api/src/infrastructure/*.repository.ts`; `cli/src/commands/init.{ts,factory,prompter,presenter}.ts`
alongside `cli/src/infrastructure/*-store.ts`, `api-client.ts`, `git-repository.ts`,
`project-directory.ts`). This plan is written against that current layout.

## API slice

**Repository boundary**: `ProjectRepository` never persists a `Skill` on its own — only the whole
`Project` aggregate, in one operation. No `saveSkills` method.

1. **`api/src/core/domain/skill.ts`** (new) — flat child entity, private constructor:

   ```ts
   export class Skill {
     private constructor(readonly id: string, readonly projectId: string, readonly name: string) {}
     static create(projectId: string, name: string): Skill // id: `skill_${nanoid()}`
     static reconstitute(data: { id: string; projectId: string; name: string }): Skill
   }
   ```

2. **`api/src/core/domain/project.ts`**:

   + `id`/`name`/`gitRepository` become `private readonly` (currently public — used directly by
     `RegisterProject`/`ProjectRepository`, both need to switch to `.snapshot()`). Add
     `private readonly skills: Skill[]`.
   + `snapshot(): ProjectSnapshot` where
     `ProjectSnapshot = { id, name, repoKey, remoteUrl, skills: ReadonlyArray<{id, name}> }` — build
     `skills` via `.map()` into fresh plain objects, never return the live `Skill[]` reference.
   + `registerSkills(names: string[]): void | DuplicateSkillNameError` (new error class in this
     file) — `names` containing duplicates → return the error, no mutation. Otherwise: reuse an
     existing `Skill` by name, `Skill.create(this.id, name)` for a new one, mutate `this.skills` in
     place. Void return — callers read the outcome via `snapshot()` afterward.
   + `reconstitute(data)` gains an optional `skills?: Skill[]` param (default `[]`) — the existing
     `getByRepoKey` call site doesn't pass it and doesn't need to change otherwise.

3. **`api/src/infrastructure/project.repository.ts`**:
   + `addNewProject`/`getByRepoKey` switch their field reads to `project.snapshot()`.
   + New `findById(id): Project | undefined` — `SELECT` the project row plus its skill rows
     (separate query keyed by `project_id`, or a join — either is fine), `undefined` if the project
     row is missing, else `Project.reconstitute` with `skills: rows.map(Skill.reconstitute)`.
   + New `save(project: Project): void` — wraps in `this.db.transaction(...)`: upsert the project
     row (`ON CONFLICT(id) DO NOTHING` — this use case never renames a project, so no need to
     handle an update), then batch-insert every skill from `snapshot().skills`
     (`ON CONFLICT(project_id, name) DO NOTHING`). One method, one transaction, whole aggregate.

4. **`api/src/infrastructure/db/migrations.ts`** — version 3:

   ```sql
   -- up
   CREATE TABLE IF NOT EXISTS skills (
     id         TEXT NOT NULL PRIMARY KEY,
     project_id TEXT NOT NULL,
     name       TEXT NOT NULL,
     UNIQUE(project_id, name),
     FOREIGN KEY(project_id) REFERENCES projects(id)
   )
   -- down
   DROP TABLE IF EXISTS skills
   ```

   Also add `db.pragma('foreign_keys = ON')` right after both `new Database(...)` call sites
   (`api/src/index.ts` and `api/tests/helpers/create-test-db.ts`) — this codebase never sets it
   today; new for this story, needed for the `FOREIGN KEY` above to actually be enforced.

5. **`api/src/core/use-cases/register-skills-into-project.ts`** (new) —
   `RegisterSkillsIntoProject`, constructor-injected `ProjectRepository`:
   + New `UnknownProjectError` (use-case-local, not a domain invariant).
   + `run(projectId, names)`: `findById` → `UnknownProjectError` if missing → `project.registerSkills(names)`
     → passthrough `DuplicateSkillNameError` → `repository.save(project)` → map `names` to
     `{name, skillId}` by looking each one up in `project.snapshot().skills` (the snapshot is the
     single source of truth for the assigned ids; the use-case never computes an id itself).

6. **`api/src/endpoints/contracts/skills.ts`** (new) —
   `RegisterSkillsRequestBody { skills: Array<{ name: string }> }`,
   `SkillResponseBodyItem { name: string; skillId: string }`.

7. **`api/src/endpoints/skill.endpoints.ts`** (new) — `POST /projects/:id/skills` (registered with
   `prefix: '/api'` in `app.ts`, same as `projectEndpoints`, giving the full
   `/api/projects/:id/skills`). JSON schema: `id` param non-empty; each `skills[].name` non-empty
   and matching `^[^:]+$` (rejects namespaced names) → both collapse to a single schema-level 400,
   no separate hand-written check. `UnknownProjectError` → 404. `DuplicateSkillNameError` → 422.
   Wire `RegisterSkillsIntoProject` into `app.ts` next to the existing use-cases.

8. **`api/tests/endpoints/skill.endpoints.test.ts`** (new) — one `fastify.inject()` case per
   Acceptance Criteria bullet (8 cases): no-skills-yet/200, repeat-same-names/same-ids,
   mixed-existing-and-new/one-response, unknown-project/404, missing-or-empty-name/400,
   namespaced-name/400, duplicate-names-in-request/422, empty-array/200-`[]`.

## CLI slice

**No new infrastructure module for scanning.** `GitRepository` is already this package's one typed
factory for all git CLI access (`cli/STANDARDS.md`) — extend it instead of adding a
`skill-scanner.ts` that would sit outside that list:

+ New `GitRepository` methods: resolve whether local `main` exists (throw/return an error result if
  not — no `origin/main` fallback), list `.claude/skills/*/SKILL.md` paths at a ref (`git ls-tree`),
  read a file's content at a ref (`git show`).
+ Frontmatter parsing + skip-classification (namespaced / malformed) is pure logic with no I/O of
  its own — per outside-in TDD, build it inline in `init.ts` first; only extract to its own file if
  a later case demands reuse.

1. **`cli/src/infrastructure/git-repository.ts`** — add the git-plumbing methods above.

2. **`cli/src/infrastructure/cache-store.ts`** — `RipeCache` gains `skillIds?: Record<string, string>`;
   `CacheStore` gains `read(): RipeCache | undefined`, mirroring `SettingsStore.read()`'s exact
   missing-file/invalid-JSON/failed-shape-check → `undefined` pattern. `write()` stays a plain full
   overwrite — no partial-update support needed, since a successful sync always replaces `skillIds`
   wholesale, never merges.

3. **`cli/src/infrastructure/api-client.ts`** — add `registerSkills(projectId, names): Promise<{name, skillId}[]>`
   POSTing to `/api/projects/${projectId}/skills`, same error-handling shape as `registerProject`.

4. **`cli/src/commands/init.ts`** — after project registration succeeds:
   + Read the cache *once*, before project registration, so its `skillIds` survive being threaded
     through even if a later step fails.
   + Scan skills via the extended `GitRepository`; no local `main` → presenter error, command
     returns `'error'` (same shape as the existing remote-url-error path), no POST.
   + No skills found → presenter warning, no POST.
   + Compare scanned names to cached `skillIds` keys — identical → skip the POST entirely;
     different (including "cache was empty" and "cache had a different, non-empty set") → POST the
     full scanned catalog, then overwrite `skillIds` in the cache with the response.
   + Skipped skills (namespaced/malformed) print a presenter warning each; "not committed on main"
     needs no warning (it's simply absent from what `git ls-tree` returns).

5. **`cli/src/commands/init.presenter.ts`** — new warning-only `on*` methods for: no local `main`,
   no skills found, a skipped skill (namespaced/malformed), skill-registration network failure.

6. **`cli/package.json`** — bump `0.2.0` → `0.3.0`, as the last step before opening the PR.

7. **`cli/tests/commands/init.test.ts`** — extend the existing (or add a) `describe('skill
   registration')` block, real tmpdir git repo + real commits (same pattern as the rest of the
   file), `nock` for the HTTP boundary only:
   + full catalog registered from an empty cache
   + identical scanned/cached name sets → no network call at all (assert via `nock`'s no-pending-
     mocks/no-unmatched-request)
   + a non-empty cached `skillIds` that no longer matches the scan → full catalog re-POSTed, cache
     overwritten
   + no skills found → warning, no POST
   + `it.each` over the two skip reasons (namespaced, malformed frontmatter) — excluded from the
     POST body and the cache, each also prints a warning
   + a skill only on a feature branch / left uncommitted → excluded, no warning
   + no local `main` branch → stderr error, exit 1, no POST

## Not in scope

+ Skill deletion/archival, rename detection (V2), `ripe sync`'s own lazy skill resolution (US-2.2).

2. `pnpm --filter ./cli build`, then run the built CLI's `init` against a scratch tmpdir git repo
   (real `git init`, a commit on `main` with a couple of `.claude/skills/*/SKILL.md` fixtures,
   `git remote add origin <any https url>`) pointed at the local server from step 1.
3. Confirm: first run registers the project and POSTs the skill catalog (check server logs / a
   `GET /api/projects` call, and inspect `.ripe/cache.json` for `skillIds`); second run makes no
   skill POST (add nothing, re-run, confirm via server log silence on `/skills`); add one more
   skill file + commit, re-run, confirm only the new skill triggers a POST and the cache updates.

## Execution notes

Two implementers, dispatched in parallel — **API** (files 1–8 above) and **CLI** (files 1–7 above)
touch fully disjoint paths (`api/src/**`/`api/tests/**` vs `cli/src/**`/`cli/tests/**`), and the CLI
side only needs the wire contract already fixed in the spec doc (path, body/response shape, status
codes) — it mocks the HTTP boundary with `nock` regardless of whether the real API endpoint exists
yet. No shared state, so no need to wait for one before starting the other.

**TDD, outside-in, per slice:**

+ **API**: failing `skill.endpoints.test.ts` cases first (one at a time, simplest case — no skills
  yet — before the others), building out `Skill`/`Project.registerSkills`/`snapshot`/
  `ProjectRepository.findById`/`save`/the use-case/the endpoint only as each case demands it, green,
  refactor. Migration + `PRAGMA foreign_keys` land first since every other piece depends on the
  `skills` table existing.
+ **CLI**: failing `init.test.ts` cases first (simplest — full catalog from empty cache — before
  the rest), extending `GitRepository`/`CacheStore`/`ApiClient`/`init.ts`/`init.presenter.ts` only
  as each case demands it, green, refactor.

After both land: review (this repo's `iteration-code-review` skill) → verify-and-fix
(`iteration-verify-and-fix`) → the manual e2e pass above → recap + PR (`iteration-recap`) → mark
the user story `Done`.
